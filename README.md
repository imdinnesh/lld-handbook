# Low-Level Design (LLD) & Object-Oriented Programming (OOP) Notes

This directory contains a collection of comprehensive notes and examples on core Object-Oriented Programming (OOP) concepts and Low-Level Design (LLD) principles. 

## Table of Contents

1. [Class and Objects](./01.ClassObjects.md)
   - Introduction to classes, objects, and basic OOP principles.
2. [Enums](./02.Enums.md)
   - Using enumerations for predefined constants.
3. [Interfaces](./03.Interface.md)
   - Defining contracts and achieving abstraction.
4. [Encapsulation](./04.Encapsulation.md)
   - Data hiding and protecting object state.
5. [Abstraction](./05.Abstraction.md)
   - Hiding implementation details and showing only essential features.
6. [Inheritance](./06.Inheritance.md)
   - Reusability and extending existing classes.
7. [Polymorphism](./07.Polymorphism.md)
   - Method overloading, overriding, and dynamic method dispatch.
8. [Association](./08.Association.md)
   - Defining relationships between objects where each has an independent lifecycle.
9. [Aggregation](./09.Aggregation.md)
   - A specialized form of association indicating a "has-a" relationship where the child can exist independently of the parent.
10. [Composition](./10.Composition.md)
    - A strong "has-a" relationship where the child's lifecycle is strictly tied to the parent's lifecycle.
11. [Dependency](./11.Dependency.md)
    - Representing a "uses-a" relationship where changes to one class may affect another.
12. [Realization](./12.Realization.md)
    - Implementing an interface or abstraction, bridging the gap between definition and implementation.
13. [DRY Principle](./13.DryPrinciples.md)
    - "Don't Repeat Yourself" – ensuring every piece of knowledge has a single, unambiguous, authoritative representation.
14. [KISS Principle](./14.KISS.md)
    - "Keep It Simple, Stupid" – focusing on writing the simplest sufficient code to minimize bugs and overhead.
15. [YAGNI Principle](./15.YAGNI.md)
    - "You Aren't Gonna Need It" – avoiding over-engineering and speculative features until they are actually needed.
16. [Law of Demeter](./16.LOD.md)
    - The Principle of Least Knowledge – keeping object interactions clean and localized to immediate collaborators, avoiding dot-chaining.
17. [Separation of Concerns](./17.SOC.md)
    - Dividing a program into distinct sections, where each section addresses a single domain responsibility or technical layer.
18. [Coupling and Cohesion](./18.COC.md)
    - Maximizing internal focus (cohesion) within modules while minimizing external dependencies (coupling) between them.
19. [Composing Objects Principle](./19.COP.md)
    - Favoring composition over inheritance to build flexible, runtime-interchangeable components without class explosion.
20. [Single Responsibility Principle](./20.SRP.md)
    - "A class should have one, and only one, reason to change" – focusing on small, cohesive classes that do one thing and do it well.
21. [Open-Closed Principle](./21.OCP.md)
    - "Software entities should be open for extension, but closed for modification" – using abstraction to welcome new behavior without touching old code.
